# UI 多角色会诊审查

单一视角审查会漏东西。**伪装成五个不同专业的审查者，各自只看自己关心的东西**，
再把意见汇总——比一次性「看看好不好看」有效得多。

## 为什么有效

一个人（或一个模型）看界面时，注意力会被最显眼的问题吸走，
剩下四类问题就看不见了。**强制分视角**能逼出被忽略的维度：

| 角色 | 只关心 | 典型发现 |
| --- | --- | --- |
| UX 设计师 | 流程、信息层级、上手成本 | 「空状态没有引导」「要点三次才找到」 |
| 视觉设计师 | 对齐、间距、色彩、层次 | 「两种主色打架」「卡片间距不一致」 |
| 无障碍专家 | 对比度、语义、键盘、触控 | 「这个按钮才 21px 高」「对比度 1.4」 |
| 移动端专家 | 单手可达、滚动、遮挡、安全区 | 「主操作被底栏挡住」 |
| 文案设计师 | 措辞、一致性、语气、错误提示 | 「报错只说失败了，没说怎么办」 |

## 执行流程

### 第 1 步：取证

先跑布局审计 + 截图，拿到客观数据和可视材料：

```bash
node scripts/audit-ui.mjs http://127.0.0.1:8787              # 移动浅色
node scripts/audit-ui.mjs --dark                              # 移动深色
node scripts/audit-ui.mjs --desktop                           # 桌面
```

输出：`.audit/<组合>/*.png` 逐页截图 + `report-<组合>.json` 量化问题清单。

**必须实际看图**。数字查不出「丑」，只能查出「错」。

截图过大先缩放：
```bash
ffmpeg -y -v error -i page.png -vf "scale=iw*0.5:-1" small.png
```

### 第 2 步：五视角独立审查

**对每个页面，依次切换到五个角色各看一遍**，每个角色只记录自己领域的问题。
不要一次看完综合判断——那样会退化成单一视角。

每发现一个问题，记录四要素：

```
【角色】无障碍
【页面】日历
【问题】日期格子 42×42，小于舒适触控尺寸
【影响】拇指容易点错相邻日期，月末选错日子
【建议】提到 44×44 以上，或加大格子间距
```

### 第 3 步：汇总去重

同一个问题可能被多个角色发现（例如「按钮太小」会被无障碍和移动端同时指出）。
按**根因**合并，不按表象合并。

然后按严重度排序：

| 级别 | 判定标准 |
| --- | --- |
| **高** | 功能不可用 / 信息看不清 / 误操作风险 |
| **中** | 明显影响效率或体验，有绕路方案 |
| **低** | 打磨项，不影响完成任务 |

### 第 4 步：修复 → 回归 → 复看

改完必须**重新截图复看**，不能只看审计数字变绿。
布局审计 0 问题 ≠ 好看。

## 各角色的具体检查清单

### UX 设计师

- [ ] 新用户第一眼知道该干什么吗？（空状态有引导吗）
- [ ] 主操作在首屏可见吗？需要滚动几次才能触达？
- [ ] 信息层级是否清楚——一眼能分出主次？
- [ ] 完成一个常见任务的步骤数合理吗？
- [ ] 有没有「点了没反馈」的操作？
- [ ] 错误状态是否给出**下一步该怎么做**，而不只是「失败了」？
- [ ] 返回/撤销路径存在吗？（删了能恢复吗）

### 视觉设计师

- [ ] 间距是否成体系（4/8/12/16/24），还是各写各的？
- [ ] 圆角是否统一？同类元素半径一致吗？
- [ ] 主色是否克制？一屏里出现几种强调色？
- [ ] 深浅层次够不够——卡片和背景能分开吗？
- [ ] 对齐：左边缘是否在同一条竖线上？
- [ ] 字重层次：标题/正文/辅助 是否分得开？
- [ ] 是否有「半成品感」：默认样式、未对齐、贴边、文字截断

### 无障碍专家

- [ ] 正文对比度 ≥ 4.5，大字 ≥ 3（用公式算，别目测）
- [ ] 触控目标 ≥ 44×44（移动）/ 32×32（桌面）
- [ ] 交互元素有 `aria-label` 或可读文本吗
- [ ] 键盘能走通主流程吗（Tab / Enter / 方向键）
- [ ] 图标按钮是否只有图标没有文字标签（需 aria-label）
- [ ] 状态变化是否只用颜色表达（色盲不友好）
- [ ] `prefers-reduced-motion` 是否被尊重

### 移动端专家

- [ ] 360px 宽下有没有横向滚动
- [ ] 底部固定元素（导航/输入框）有没有挡住内容
- [ ] 单手可达：主操作在屏幕下半部分吗
- [ ] 输入框聚焦时会不会被键盘遮住
- [ ] 长列表滚动性能如何（虚拟化了吗）
- [ ] 安全区适配（`env(safe-area-inset-*)`）
- [ ] 弹层能否下滑关闭、点遮罩关闭

### 文案设计师

- [ ] 按钮文案是动词还是名词？（「记一笔」优于「确定」）
- [ ] 同一概念是否用同一个词（别一处「记录」一处「笔记」）
- [ ] 空状态文案是否友好、给出行动建议
- [ ] 报错是否说清「哪里错、怎么办」
- [ ] 语气是否一致（别一半正式一半俏皮）
- [ ] 有没有技术术语泄漏给用户（「tokens」「API」）
- [ ] 数字与单位格式统一吗

## 报告格式

汇总后输出：

```markdown
## UI 审查报告

### 高（必须修）
1. [无障碍/移动] 日历格子 42×42 → 提到 48×48
2. [UX] 空状态无引导 → 加「记一笔」按钮

### 中（建议修）
3. [视觉] 卡片间距 8/9/10 混用 → 统一为 8
4. [文案] 「请求失败（200）」→ 说清原因和下一步

### 低（打磨）
5. [视觉] 图例色块与格子色值略有偏差

### 已确认没问题
- 键盘可走通主流程
- 深色模式对比度全部达标
```

**「已确认没问题」这一节很重要**——它记录了检查过的范围，
避免下次重复审查同样的东西。
